The module is a thin FastAPI application layer that wires Pydantic request/response schemas (in `schemas.py`) to singleton service instances under `services/`.

- Entry point: `main.py` creates the `FastAPI` app with an `asynccontextmanager` lifespan that eagerly loads the category classifier and manufacturer resolver; CORS middleware is enabled for all origins.
- Configuration: `config.py` defines a single `Settings` Pydantic model loaded from environment variables (`MODEL_DIR`, `CATEGORY_MODEL_PATH`, `ONNX_*`, etc.) with sensible defaults pointing at sibling `apps/ml/models`.
- Services directory holds one class-per-capability singleton (`category_classifier`, `manufacturer_resolver`, `duplicate_detector`, `datasheet_extractor`, `attribute_intelligence_service`, `model_registry`, `training_runner`). Each exposes a small stable interface (`load`, `predict`, `resolve`, `detect`, `process`, `suggest_*`, `audit_library`) consumed by route handlers.
- Two logical endpoint groups share the same URL space:
  - Public-facing `/v1/predict/*`, `/v1/resolve/*`, `/v1/detect/*`, `/v1/extract/*`, `/v1/suggest`, and the full `/v1/attributes/*` suite (RFC-0059) which compose multiple services inside a single handler (e.g. `suggest_component` runs category + manufacturer + duplicate + extraction then aggregates evidence).
  - Internal ML operations under `/v1/training/*` and `/v1/models/*` — documented as never called from a browser; only the authenticated NestJS API calls them. These routes delegate to `TrainingRunner`, which runs the existing pipeline (`apps/ml/pipeline/*`) on a background thread and keeps in-memory run state while the durable record lives in PostgreSQL via the API.
- Dependency direction is strictly one-way: `main.py` → `services/*` → `config.py` / `schemas.py`; services do not import route handlers. Cross-service coupling is minimal (e.g. `training_runner` imports `model_registry` and `category_classifier` to inspect active artifacts).

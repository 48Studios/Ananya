All collectors subclass `BaseCollector` (base.py), which defines the abstract `collect(**kwargs) -> List[ProductRecord]` contract plus shared `validate()` and `persist_raw()` helpers that write JSON + a SHA-256 checksummed `DatasetManifest`. Concrete collectors live as one class per source type:
- `AnanyaDbCollector` (ananya_db.py) — reads pre-dumped JSON snapshots or connects to a live PostgreSQL via optional `psycopg2`, mapping components/categories/manufacturers/attribute values/document refs into `ProductRecord`s; exposes a module-level `infer_domain(category_name)` helper used by other collectors.
- `ManufacturerCatalogCollector` (catalog.py) — parses local `.json` / `.csv` / `.tsv` manufacturer files.
- `DistributorFeedCollector` (distributor.py) — parses JSON distributor feeds (DigiKey, Mouser, etc.).
- `DocumentCollector` (documents.py) — ingests a JSON index of datasheets/manuals and attaches `DocumentRefRecord`s.
- `AutonomousWebCollector` (web_collector.py) — the heavyweight crawler: loads `SourceRegistry` from `sources.yaml`, drives `DiscoveryEngine` → `ResilientDownloader` → `ContentExtractor` across configured sources, persists crawl state in an `AcquisitionStore`, and on completion runs the downstream pipeline (Normalization → Validation → Deduplication → Dataset Generators → Splitting).

Dependency direction is strictly inward: collectors depend on `..schemas.product`, `..schemas.manifest`, `..config.settings`, and sibling `web.*` subpackage modules (`registry`, `policy`, `downloader`, `acquisition`, `discovery`, `extractor`); they never import each other. The `web_collector` additionally reaches into `..processors.*`, `..generators.*`, `..datasets.splitter`, `..coverage`, and `..tui` to bridge collection with the rest of the training pipeline.

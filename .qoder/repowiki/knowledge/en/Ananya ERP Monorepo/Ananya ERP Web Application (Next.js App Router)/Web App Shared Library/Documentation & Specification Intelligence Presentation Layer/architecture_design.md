Three sibling modules form a layered presentation facade over the API DTOs in `./api/*`, with no DOM or framework dependencies so they can be unit-tested in isolation.

- `document-intelligence.ts` owns per-document analysis UX: eligibility gating (`deriveAnalyzeAction`), status/evidence/candidate rendering, summary row construction, and immutable local-state reducers (`applyAnalysisState`, `mergeAnalysisResult`, `markAnalysisInProgress`) keyed by document id. It enforces the advisory stance — extracted values are suggestions requiring human acceptance via the Component Review Queue.
- `intelligence-review-filters.ts` is a shared vocabulary layer defining the canonical lifecycle statuses (`PENDING`, `ACCEPTED`, `REJECTED`, `DISMISSED`, `STALE`), confidence bands (`HIGH`, `MEDIUM`, `LOW`), and filter helpers (`matchesStatusFilter`, `matchesConfidenceFilter`, `filterValueToParam`). All three intelligence surfaces (Component, Attribute, Documentation) consume this module to keep label semantics consistent across queues.
- `specification-intelligence.ts` aggregates per-specification evidence into reviewable rows: conflict detection copy, ERP comparison text, ambiguity handling for unmapped properties, confidence bucketing/thresholds, tab/filter computation (`SPECIFICATION_FILTERS`, `buildSpecificationFilterCounts`, `filterSpecifications`), and optimistic local updates (`applyDecisionToSpecifications`, `applyApplicationToSpecifications`, `withUpdatedSpecifications`) matched by finding fingerprint.

Dependency direction is one-way: `specification-intelligence.ts` imports from `intelligence-review-filters.ts`; both import only type declarations from the API modules, never calling them directly. This keeps business rules testable without network or React.

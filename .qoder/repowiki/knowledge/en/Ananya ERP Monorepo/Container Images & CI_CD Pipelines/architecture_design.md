Two cooperating concerns live side by side:

- `docker/` holds one hardened multi-stage Dockerfile per service (`Dockerfile.api`, `Dockerfile.web`, `Dockerfile.worker`, `Dockerfile.ml`). Each follows a fixed four-stage pattern — pruner (turbo prune scoped to the package), builder (pnpm install + turbo build), prod-deps (production-only node_modules), runner (non-root `ananya` user UID/GID 10001) — and uses `node:22-alpine` with BuildKit cache mounts. The web image is Next.js standalone; the API/worker images expose `/health`; the ML image targets CPU-first Python/FastAPI. A `README.md` documents Compose profiles (`all`, `worker`, `ml`, `tools`), deployment order (PostgreSQL → migrate → api/worker/ml/web), networking, and image tag semantics.
- `.github/workflows/` defines three entry-point workflows: `ci.yml` runs `_quality-gates.yml` on push/PR to `main` and `release/*`; `docker.yml` is triggered via `workflow_run` on successful CI from `main` and publishes `edge` + `sha-<short-sha>` tags to `ghcr.io/48studios/ananya-{api,web,worker,ml}` through a matrix over the four Dockerfiles; `release.yml` triggers on `v*` tags, runs quality gates + smoke test, computes semantic version tags (`latest`, `<ver>`, `<major>.<minor>`, `<major>` when ≥1, plus prerelease channel aliases), builds multi-arch images (`linux/amd64,linux/arm64`) via QEMU, and creates a GitHub Release with auto-generated notes.

Reusable workflow fragments are factored into `_quality-gates.yml`, `_docker-smoke-test.yml`, and a shared `README.md`. Dependency direction is one-way: workflows reference Dockerfiles under `docker/`; nothing in `docker/` depends on GitHub Actions.

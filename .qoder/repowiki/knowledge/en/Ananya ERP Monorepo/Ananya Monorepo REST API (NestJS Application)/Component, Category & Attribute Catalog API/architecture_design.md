Three sibling NestJS feature modules — `components`, `categories`, `attributes` — each following the same layering: a `*.controller.ts` declares HTTP routes with per-route `UseGuards` from `../auth/*-permissions`, a `*.service.ts` holds business logic, DTOs in local files or `dtos/`, a `*.module.ts` wires providers, and a `*.tokens.ts` exports a `Symbol` used as an injection token for a repository implementation bound in the module's `providers` array.

- Data access is abstracted behind repository tokens (`COMPONENT_REPOSITORY`, `CATEGORY_REPOSITORY`, `ATTRIBUTE_DEFINITION_REPOSITORY`, etc.) resolved to `Drizzle*Repository` implementations under `../infrastructure/repositories/`, so the catalog modules never import persistence code directly.
- Cross-module dependencies flow one-way: `ComponentsModule` imports `AttributesModule`, `CategoriesModule`, `ManufacturersModule`, `MlModule` (via `forwardRef` to break the cycle through `ImportExportModule`), plus `AuthModule` and `PermissionsModule`; `AttributesModule` imports `CategoriesModule`, `UnitsModule`, `AuthModule`, `PermissionsModule`; `CategoriesModule` has no intra-catalog imports.
- Authorization is enforced at the controller level via read/write/delete guards (`ComponentReadGuard`/`WriteGuard`/`DeleteGuard`, `AttributeReadGuard`/`WriteGuard`/`DeleteGuard`) that map to `Inventory.Read` / `Inventory.Update` / `Inventory.Delete` permissions; controllers also register a class-level `@UseFilters(ComponentExceptionFilter | CategoryExceptionFilter)` for domain error mapping.
- The attributes module additionally re-exports its repository tokens so consumers can bind alternate implementations outside this module.

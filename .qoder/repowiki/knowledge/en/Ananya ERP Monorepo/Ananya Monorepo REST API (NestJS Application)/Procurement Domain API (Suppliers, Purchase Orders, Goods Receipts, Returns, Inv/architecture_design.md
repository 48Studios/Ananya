Each subdirectory is an independent NestJS `@Module` following a consistent Controller → Service → Repository pattern. Controllers declare REST routes and delegate to a service; services are `@Injectable` classes that receive their repository via a module-scoped token constant (e.g. `PURCHASE_ORDER_REPOSITORY`, `GOODS_RECEIPT_REPOSITORY`) bound in the module's `providers` array to a concrete `Drizzle*Repository` from `../infrastructure/repositories/`. Business logic lives in domain entities and use-cases imported from the shared `@ananya/procurement` package (e.g. `CreatePurchaseOrder`, `GoodsReceipt`, `PurchaseOrderRepository`), so services act as thin orchestrators that map DTOs to entity commands and persist via the repository. Cross-module dependencies flow downward: `goods-receipts` imports `purchase-orders`, `inventory-transactions`, and `inventory-projections`; `supplier-returns` imports inventory modules; `purchase-invoices` imports both `purchase-orders` and `goods-receipts`; `procurement-reporting` bypasses repositories and queries `@ananya/database` directly with Drizzle query builders. Each module exports only its service (and occasionally its repository token) to keep coupling minimal. Exception handling is per-domain via `@Catch` filters (e.g. `SupplierExceptionFilter`, `po-exception.filter.ts`, `gr-exception.filter.ts`) that translate domain errors from `@ananya/procurement` into HTTP responses.

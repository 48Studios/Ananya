The module is a NestJS `@Module` (`documents.module.ts`) that wires `DocumentsController`, `DocumentsService`, a pluggable `StorageService` (injected via the `STORAGE_PROVIDER` token), and two permission guards (`DocumentReadGuard`, `DocumentWriteGuard`). The controller delegates all business logic to `DocumentsService`, which persists records through the shared `@ananya/database` schema (`documents`, `documentVersions`, `components`) and coordinates side effects with `ActivityService` and `SecurityAuditService`. File I/O is abstracted behind `IStorageProvider` in `storage.service.ts`; only a `LocalStorageProvider` is shipped today, resolving its directory from `STORAGE_LOCAL_PATH` with a safe fallback to `<cwd>/uploads`, and path traversal is prevented via `isPathInsideDirectory`. Two document source kinds are modelled — `UPLOADED_FILE` (with per-revision storage keys) and `EXTERNAL_URL` (no stored bytes) — enforced by `document-types.ts`. Input validation is split across `dtos.ts` (class-validator decorators), `document-metadata.ts` (tags, booleans, text trimming), `document-file.ts` (MIME resolution, filename sanitization, upload size constants), and `document-url.ts` (external URL validation). Uploads go through `DocumentFileInterceptor`, which wraps multer's `FileInterceptor` and maps multer errors into documented `413`/`400` responses. Version creation uses a row-level `SELECT ... FOR UPDATE` lock inside a DB transaction to serialise concurrent revisions. Read/write access is gated by inventory permissions rather than document-specific roles.

The module is layered around a single persistence substrate (`attribute-finding.repository.ts`) accessed through an executor pattern: every repository method accepts a `DbExecutor` so callers can bind it to a transaction, and `AttributeIntelligenceFindingsService.withExecutor()` returns a service instance backed by the same logic but a transaction-scoped repository. The workflow splits into four concerns:
- Persistence substrate (`attribute-finding.repository.ts`, `attribute-finding.fingerprint.ts`, `attribute-finding.dtos.ts`) — idempotent upserts by deterministic fingerprint, guarded lifecycle transitions (PENDING/ACCEPTED/REJECTED/DISMISSED/STALE), and row locking via `for('update')`.
- Workflow service (`attribute-finding.service.ts`) — owns state-machine rules, staleness detection against live ERP rows (`attribute-finding-expected-state.ts`, `attribute-finding-live-state.ts`), decision recording with atomic feedback insertion, reconciliation of missing detections, and query normalization.
- Audit orchestration (`attribute-intelligence-audit.service.ts`) — runs the existing producer via `MlService.auditAttributeLibrary()`, snapshots authoritative library state, delegates normalization to `attribute-audit-normalizer.ts`, persists findings, and reconciles stale scope.
- HTTP boundary (`attribute-review-queue.controller.ts` + `attribute-review-queue.service.ts` + `attribute-review-apply.service.ts`) — thin projection layer with `AttributeReadGuard`/`AttributeWriteGuard`, in-process audit concurrency guard, and the only route that mutates attribute data (apply).
Dependency direction is strictly inward: controller → queue service → findings service → repository; normalizers are pure functions with no DB access. Staleness checks read live state through `readAttributeFindingLiveState` using the same executor passed down from the caller, so decision and apply paths validate against their own transaction snapshot.

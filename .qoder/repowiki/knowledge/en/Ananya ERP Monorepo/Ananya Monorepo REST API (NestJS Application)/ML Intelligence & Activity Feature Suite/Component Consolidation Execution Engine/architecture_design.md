The module is organized around an adapter pipeline orchestrated by `ComponentConsolidationService` (service.ts), which runs the entire operation inside a single Drizzle `db.transaction`. The flow is: pre-flight validation → optimistic idempotency check against persisted consolidation records → acquire pessimistic row locks via `ConsolidationLockService` (components → dependencies → findings, all in deterministic `ORDER BY id` order) → recompute and fingerprint-verify the preview → capture pre-state → run adapters in fixed order → retire sources → persist finalization. Adapters live in `adapters/` and each implements the `ConsolidationAdapter` interface from `component-consolidation.types.ts`, exposing `id`, `label`, numeric `order`, and `apply(context)` returning a typed `ConsolidationAdapterOutcome`. The dependency guard (`dependency-guard.adapter.ts`) runs first (order 5) to refuse operations when unregistered or blocking domains reference the components; inventory, attribute, BOM, supplier, procurement, batch, serial, reservation, polymorphic-reference, documentation-intelligence, finding, and retirement adapters follow in increasing order. Persistence of the operation header/results/failures is isolated in `ConsolidationRepository` (repository.ts), which writes to `consolidations` / `consolidation_sources` using the same `DbExecutor` passed through the context, ensuring every mutation is part of the transaction. `polymorphic-references.ts` centralizes the entity-type constant used by polymorphic tables. Errors are modeled as three NestJS exceptions — `ConsolidationConflictError` (409 state conflicts), `ConsolidationPlanError` (400 malformed plan), `ConsolidationAdapterBlockedError` (adapter-level blocker) — so failures roll back the whole transaction rather than leaving partial state.

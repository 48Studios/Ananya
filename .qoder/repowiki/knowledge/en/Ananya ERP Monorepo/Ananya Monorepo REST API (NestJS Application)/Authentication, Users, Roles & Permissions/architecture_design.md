Four NestJS feature modules form the identity layer. `AuthModule` (entry point) composes `UsersModule`, `PermissionsModule`, `SecurityAuditModule`, and `ActivityModule`, exposing `AuthService`, `InvitationsService`, `OnboardingService`, and `ComponentWriteGuard`. `AuthService` performs login/logout/password-reset via direct Drizzle queries against `users`, `userSessions`, and `passwordResetTokens`, records every security event through `SecurityAuditService`, and delegates role resolution to `UsersService` + `PermissionsService`. `UsersService` seeds system roles at module init by calling `RolesService.ensureSystemRoles()`, which in turn reads `SYSTEM_ROLE_PERMISSIONS` from `PermissionsService` to create built-in roles (`Administrator`, `Inventory Manager`, etc.). `PermissionsService` is a pure provider that owns the canonical `ALL_PERMISSIONS` catalogue, groups them by category, exposes `hasPermission` (supporting `*` wildcard and `domain.*` prefix), and defines the system role-to-permission map. Authorization is enforced via a single factory `createPermissionGuard(permission, subject)` in `permission.guard.ts`; domain-specific files (`component-write.guard.ts`, `attribute-permissions.ts`, `component-permissions.ts`, `ml-permissions.ts`) bind concrete permission codes to human-readable subjects and export ready-to-use guards. Dependency direction is strictly inward: controllers → services → `@ananya/database` schema/query; cross-module imports go only from `auth` → `users`/`permissions`/`security-audit`/`activity`, never the reverse.

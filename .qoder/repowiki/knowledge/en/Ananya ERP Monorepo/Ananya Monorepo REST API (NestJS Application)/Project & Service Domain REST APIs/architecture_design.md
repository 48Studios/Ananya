Each subdirectory under apps/api/src is an independent NestJS feature module following a consistent three-file layout: `<entity>.module.ts` (registers controller + service + repository provider), `<entity>.controller.ts` (thin HTTP layer with `@Controller`, `@Body`, `@Param`, `@Query`), `<entity>.service.ts` (domain orchestration), plus a local `dtos.ts` of class-validator DTOs.

- Repository abstraction: every service injects its repository via a string token (`PROJECT_REPOSITORY`, `TASK_REPOSITORY`, `TIME_ENTRY_REPOSITORY`, etc.) declared in the service file and bound in the module to a concrete `Drizzle*Repository` from `../infrastructure/repositories/`. This isolates persistence behind domain-specific repository interfaces imported from `@ananya/projects`.
- Domain model ownership: entities (Project, Task, TimeEntry, etc.) and their repository interfaces live in the shared `@ananya/projects` package; services only construct entities via static factory methods like `Project.create()` and mutate them through instance methods (`start`, `pause`, `complete`, `allocateMaterial`, …) before persisting.
- Cross-module dependencies flow downward: `time-entries` depends on `tasks`, which depends on `projects`; `projects` additionally depends on `customers`, `sales-orders`, `inventory-transactions`, and `inventory-projections` for stock validation and transaction logging during material allocate/issue/return flows.
- Business rules are enforced at the service layer (e.g., rejecting time-entry creation against DONE/CANCELLED tasks, validating available stock via `InventoryProjectionsService` before issuing materials). The `projects` module adds a custom `ProjectExceptionFilter` applied via `@UseFilters` on the controller.
- Notes and service-notes are lightweight note-taking features without cross-domain dependencies.

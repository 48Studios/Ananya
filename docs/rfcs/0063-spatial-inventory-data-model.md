# RFC-0063: Spatial Inventory Data Model

**Status:** Accepted

**Author:** Ananya Contributors

**Created:** 2026-09-30

---

# 1. Summary

This RFC defines the domain entities, relationships, persistence schema, and integrity constraints for the **Spatial Inventory** context in Ananya ERP.

The data model introduces four core entities:

1. **`SpatialModel`**: Reusable 3D/2D geometry definitions.
2. **`SpatialAnchor`**: Addressable physical sub-regions or compartments within a model.
3. **`SpatialNode`**: Placed spatial occurrences mapped directly to domain `Location` entities.
4. **`SpatialTemplate`**: Reusable parametric layout generators for multi-compartment storage.

The model strictly preserves the boundary established in [RFC-0062](0062-spatial-inventory-architecture.md): spatial data is an optional physical twin overlay that links to locations, leaving inventory ledgers ([RFC-0003](0003-inventory-ledger.md)) and projections ([RFC-0004](0004-inventory-projection.md)) untouched.

---

# 2. Motivation

In Ananya ERP, physical storage is represented by the `locations` table (`packages/database/src/schema/locations.ts`) and the warehouse hierarchy (`packages/database/src/schema/warehouses.ts` / [RFC-0021](0021-warehouse-structure-and-bin-locations.md)).

To visualize this structure spatially without corrupting the operational domain model:

- We must not inject CAD-specific or rendering-specific columns into core `locations`.
- We must avoid duplicating 3D geometry across identical storage units (e.g., twenty identical 60-drawer SMD cabinets must share a single geometry asset).
- Storage units are frequently relocated within a room; when a parent cabinet is moved, all child drawers must move naturally without requiring hundreds of database write operations.
- Components must never be linked directly to 3D meshes; all stock queries must continue to operate through standard location IDs.

## 3.1 SpatialModel

A **`SpatialModel`** represents reusable 3D geometry or 2D layout definitions.

### Characteristics:

- Geometry is decoupled from specific physical locations. A single "SMD 60-Drawer Cabinet" model can be instantiated across multiple rooms.
- The canonical browser asset format is **GLB / GLTF 2.0** for 3D and structured JSON/SVG for 2D.
- Stores physical bounding dimensions (width, height, depth in millimeters) and asset URIs.
- Does not contain inventory, location IDs, or world-space placement coordinates.

## 3.2 SpatialAnchor

A **`SpatialAnchor`** identifies a named physical point, bounding region, or sub-compartment defined relative to a `SpatialModel`'s local origin.

### Examples:

- `Drawer A1` through `Drawer F10` in a resistor cabinet.
- `Shelf Level 3, Bay B` on a heavy warehouse pallet rack.
- `Reel Slot 14` on an SMD feeder cart.

### Characteristics:

- Anchors allow a complex physical unit (such as a 60-drawer cabinet) to be represented by a single 3D mesh model rather than 60 separate asset files.
- Each anchor carries a local position, orientation, and bounding box.
- Anchors are mapped to child `Location` records via `SpatialNode` occurrences.

## 3.3 SpatialNode

A **`SpatialNode`** represents the physical instantiation of a location in spatial coordinates.

### Characteristics:

- **Location Association**: Holds a foreign key to `locations.id`.
- **Parent-Relative Transform**: Stores local position `(x, y, z)`, Euler rotation `(x, y, z)`, and scale `(x, y, z)` relative to its parent `SpatialNode`.
- **Hierarchical Derivation**: World-space coordinates are calculated recursively by traversing the `parentSpatialNodeId` tree.
- **Anchor Reference**: For sub-compartments (e.g., a specific drawer), the node references a `SpatialAnchor` on the parent model rather than loading a new geometry file.

### Why Parent-Relative Transforms:

Consider moving "Cabinet A" from position `[5.0, 0.0, 2.0]` to `[8.0, 0.0, 4.0]` in a workshop:

- With **parent-relative transforms**, only the root `SpatialNode` of Cabinet A is updated. All 60 child drawers retain their local offsets (e.g., Drawer A1 at `[0.05, 0.20, 0.00]`) and move automatically in derived world space.
- With absolute world coordinates, every move would require updating 61 distinct database rows, creating high write amplification, locking contention, and risk of desynchronization.

## 3.4 SpatialTemplate

A **`SpatialTemplate`** defines a parametric layout formula for generating repetitive storage configurations.

### Examples:

- Grid matrices: \(N\) rows by \(M\) columns of drawers.
- Bin racks: \(K\) levels with pitch \(P\).
- SMD tape reel racks with fixed slot widths.

### Characteristics:

- Templates capture layout rules (row count, column count, horizontal spacing, vertical spacing, compartment width, height, depth, naming series such as `A1..F10`).
- Templates can automatically provision child `Location` records and generate matching `SpatialAnchor` definitions upon installation.

# 4. Database Persistence Schema (PostgreSQL / Drizzle ORM)

The relational schema integrates cleanly into `packages/database/src/schema/` following existing Ananya naming and type conventions.

```sql
-- 1. Spatial Models (Reusable 3D/2D Assets)
CREATE TABLE spatial_models (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  code VARCHAR(64) NOT NULL UNIQUE,
  name VARCHAR(128) NOT NULL,
  description TEXT,
  format VARCHAR(32) NOT NULL DEFAULT 'GLB',          -- GLB, GLTF, SVG, PROCEDURAL
  asset_uri VARCHAR(512),                             -- S3/CDN object storage path
  thumbnail_uri VARCHAR(512),
  width_mm NUMERIC(10, 2) NOT NULL,                   -- Bounding dimensions in mm
  height_mm NUMERIC(10, 2) NOT NULL,
  depth_mm NUMERIC(10, 2) NOT NULL,
  metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
  is_active BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX spatial_models_code_idx ON spatial_models(code);
CREATE INDEX spatial_models_format_idx ON spatial_models(format);

-- 2. Spatial Anchors (Sub-compartments within a model)
CREATE TABLE spatial_anchors (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  model_id UUID NOT NULL REFERENCES spatial_models(id) ON DELETE CASCADE,
  code VARCHAR(64) NOT NULL,                          -- e.g. "DRAWER-A1", "SLOT-04"
  name VARCHAR(128) NOT NULL,
  anchor_type VARCHAR(32) NOT NULL DEFAULT 'BIN',     -- BIN, DRAWER, SHELF, MOUNT, ACCESS
  local_position_x NUMERIC(10, 4) NOT NULL DEFAULT 0, -- Meters relative to model origin
  local_position_y NUMERIC(10, 4) NOT NULL DEFAULT 0,
  local_position_z NUMERIC(10, 4) NOT NULL DEFAULT 0,
  local_rotation_x NUMERIC(8, 4) NOT NULL DEFAULT 0,  -- Degrees
  local_rotation_y NUMERIC(8, 4) NOT NULL DEFAULT 0,
  local_rotation_z NUMERIC(8, 4) NOT NULL DEFAULT 0,
  bounding_width_mm NUMERIC(10, 2),
  bounding_height_mm NUMERIC(10, 2),
  bounding_depth_mm NUMERIC(10, 2),
  metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE UNIQUE INDEX spatial_anchors_model_code_unique ON spatial_anchors(model_id, code);
CREATE INDEX spatial_anchors_model_id_idx ON spatial_anchors(model_id);

-- 3. Spatial Nodes (Physical occurrence mapped to Location)
CREATE TABLE spatial_nodes (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  location_id UUID NOT NULL UNIQUE REFERENCES locations(id) ON DELETE CASCADE,
  model_id UUID REFERENCES spatial_models(id) ON DELETE RESTRICT,
  parent_spatial_node_id UUID REFERENCES spatial_nodes(id) ON DELETE SET NULL,
  anchor_id UUID REFERENCES spatial_anchors(id) ON DELETE SET NULL,

  -- Transform relative to parent spatial node (or world if root)
  position_x NUMERIC(10, 4) NOT NULL DEFAULT 0,       -- Meters
  position_y NUMERIC(10, 4) NOT NULL DEFAULT 0,
  position_z NUMERIC(10, 4) NOT NULL DEFAULT 0,

  rotation_x NUMERIC(8, 4) NOT NULL DEFAULT 0,        -- Degrees
  rotation_y NUMERIC(8, 4) NOT NULL DEFAULT 0,
  rotation_z NUMERIC(8, 4) NOT NULL DEFAULT 0,

  scale_x NUMERIC(6, 4) NOT NULL DEFAULT 1.0000,
  scale_y NUMERIC(6, 4) NOT NULL DEFAULT 1.0000,
  scale_z NUMERIC(6, 4) NOT NULL DEFAULT 1.0000,

  is_visible BOOLEAN NOT NULL DEFAULT TRUE,
  metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX spatial_nodes_location_id_idx ON spatial_nodes(location_id);
CREATE INDEX spatial_nodes_model_id_idx ON spatial_nodes(model_id);
CREATE INDEX spatial_nodes_parent_id_idx ON spatial_nodes(parent_spatial_node_id);
CREATE INDEX spatial_nodes_anchor_id_idx ON spatial_nodes(anchor_id);

-- 4. Spatial Templates (Parametric storage layouts)
CREATE TABLE spatial_templates (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  code VARCHAR(64) NOT NULL UNIQUE,
  name VARCHAR(128) NOT NULL,
  description TEXT,
  category VARCHAR(64) NOT NULL DEFAULT 'DRAWER_CABINET', -- DRAWER_CABINET, PALLET_RACK, REEL_RACK, BIN_GRID
  rows INTEGER NOT NULL DEFAULT 1,
  columns INTEGER NOT NULL DEFAULT 1,
  levels INTEGER NOT NULL DEFAULT 1,
  unit_width_mm NUMERIC(10, 2) NOT NULL,
  unit_height_mm NUMERIC(10, 2) NOT NULL,
  unit_depth_mm NUMERIC(10, 2) NOT NULL,
  spacing_x_mm NUMERIC(10, 2) NOT NULL DEFAULT 0,
  spacing_y_mm NUMERIC(10, 2) NOT NULL DEFAULT 0,
  naming_pattern VARCHAR(128) NOT NULL DEFAULT 'R{row}C{col}', -- Template string
  associated_model_id UUID REFERENCES spatial_models(id) ON DELETE SET NULL,
  metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX spatial_templates_code_idx ON spatial_templates(code);
CREATE INDEX spatial_templates_category_idx ON spatial_templates(category);
```

# 6. Domain Invariants & Integrity Constraints

1. **Location Uniqueness**: `location_id` in `spatial_nodes` has a `UNIQUE` constraint. A domain `Location` may have at most one physical spatial representation.
2. **Referential Integrity**:
   - `spatial_nodes.location_id` enforces foreign key reference to `locations.id`.
   - If a domain `Location` is removed through authorized warehouse procedures, the corresponding `spatial_nodes` record is deleted (`ON DELETE CASCADE`), ensuring zero orphaned spatial records.
   - Deleting a `spatial_models` record is restricted (`ON DELETE RESTRICT`) if active `spatial_nodes` are referencing it.
3. **No Mesh-to-Inventory Linkage**: There is no table, column, or relation linking `components` directly to `spatial_models`, meshes, or coordinates. All inventory queries remain:
   ```text
   Component ──> inventory_projections ──> locations ──> spatial_nodes
   ```
4. **Hierarchy Cycle Prevention**: A `SpatialNode` cannot have itself as its parent or create a cyclic parentage loop. Traversal validation is enforced at the domain service layer.
5. **Ledger Immutability Guarantee**: Spatial domain services and repositories possess zero permissions to insert or mutate records in `inventory_transactions` or `inventory_projections`.

# 7. Model/Location Separation Case Study

Consider re-organizing a physical laboratory bench:

- A user moves "SMD Resistor Cabinet 01" from Workbench East to Workbench West.
- In the spatial layer, `spatial_nodes.position_x` and `position_z` for the cabinet are updated.
- **Inventory consequence**: Exact zero rows in `inventory_transactions`, `inventory_projections`, `components`, or `locations` are modified. All stock levels remain valid and audit logs remain untouched.
- Now consider moving a reel of 100nF capacitors from Drawer A1 to Drawer B4.
- In the inventory layer, an `InventoryTransaction` of type `TRANSFER` is executed ([RFC-0005](0005-transaction-types.md), [RFC-0024](0024-warehouse-transfers.md)), updating `inventory_projections`.
- **Spatial consequence**: Exact zero rows in `spatial_nodes`, `spatial_models`, or `spatial_anchors` are modified. The spatial viewer simply queries current projections and highlights Drawer B4 instead of Drawer A1.

# 8. Migration & Deployment Strategy

- **Zero-Downtime Schema Application**: The four new tables (`spatial_models`, `spatial_anchors`, `spatial_nodes`, `spatial_templates`) are additive and do not alter or lock existing tables.
- **Data Pack Bootstrapping**: Standard equipment models (e.g., 60-drawer SMD cabinet, 4-tier warehouse rack, ESD bench) are delivered via Ananya Data Packs (`/settings/data-packs`) per [ARCHITECTURE.md](../../ARCHITECTURE.md), eliminating raw CLI database seeding.
